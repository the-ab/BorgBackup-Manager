Operations manual

Using BorgBackup Manager

This manual covers all features in version 1.1.1, from installation and sign-in through devices, repositories, jobs and schedules to archive management, restore, user permissions and diagnostics.

1. Quick start and system layout

The manager runs as a Docker container and controls Borg centrally. For a backup, the manager starts Borg on the selected client over SSH. The client reads its local files and writes to the configured repository. Clients do not need separate backup scripts or cron jobs.

Under Infrastructure, the sidebar now contains only Devices and System. The System workspace combines Notifications, Users, Manager backup, Settings and System diagnostics in one tab row. Diagnostics are no longer shown on the dashboard. The tab row and active selection are restored after a page reload or direct System link.

  1. Sign in as an administrator and add the public controller key to the client's authorized_keys.
  2. Add the device, verify its Ed25519 fingerprint and detect its Borg version.
  3. Create a managed or external repository, or import an existing local repository.
  4. Save a backup job with device, repository, sources, exclusions, compression and retention.
  5. Configure repository access directly on the backup job.
  6. Optionally assign a central schedule.
  7. Test the connection and run a small test backup.
  8. Browse an archive and test restore with a dry run first.
Important paths: manager data /data, repositories /repositories, run logs /data/run-logs, archive cache /data/archive-cache, manager Borg cache /data/borg-cache/repository-<ID>, device cache $HOME/.cache/borgbackup-manager/repository-<ID>, and security data /data/security.

2. HTTPS, sign-in and security data

Sign-in

  • Personal accounts with role-based access.
  • Passwords stored as salted scrypt verifiers.
  • Server-side revocable sessions with an HttpOnly cookie.
  • A tab-bound reload session as a secured fallback.
  • Source-scoped login rate limits without a globally abusable account lock.

Secrets

  • Repository passphrases, Borg keyfiles, and private SSH/TLS keys are encrypted with the master key.
  • /data/security/security.db contains users, sessions and encrypted secrets.
  • /data/security/master.key is the external trust anchor and must be backed up.

The initial password can be displayed with python -m app.initial_admin. Use ./recovery.sh in the project directory for account recovery, unlock and password reset.

3. Dashboard and active tasks

The dashboard shows job counts, running, queued and failed runs, plus repository count and total size. The Backup Jobs panel includes status, device, repository, sources, schedule, latest run, size of the latest successful backup, and a direct start button. Source statistics and latest-run details use two compact rows; deduplicated, original and compressed sizes use three tightly spaced label/value rows. It can be sorted by name, status, device, repository, latest run or backup size.

The status control next to the theme button always represents the current running task. Clicking it opens that task's live log directly, without an intermediate menu. If no task is running but one is queued, it opens the next queued run. After completion, the same area briefly shows the action result.

Attention highlights critical or outdated Borg versions, missing repository access and failed runs. System diagnostics are loaded, refreshed and closed under System → System diagnostics.

5. Repositories

Local import: automatic search scans safely up to six levels below /repositories; the folder browser can select nested Borg repositories and the current directory when it contains config. The repository bind uses Linux rslave propagation so remounted host/NFS submounts can become visible without restarting the container. Use “Refresh status” after remounting; reset only if a repository was actually deleted.

Repositories can be sorted by name, readiness, type, job count or size. The choice is retained for the signed-in user in this browser. The table shows the numeric manager ID of each repository record directly beside its status; it is the same ID used in manager-side and device-side BBM cache paths such as repository-<ID>.

Managed

Stored below /repositories. Archive listing, check, prune, compact, diff and browsing run locally in the manager. Clients write through the integrated repository SSH service.

External

Uses an existing Borg URL. SSH keys and host key are managed centrally; no backup job is required to display archives.

  • Search automatically detects existing local Borg repositories. Select folder opens a path-contained browser below /repositories for deliberate selection; symbolic links are not opened. Import Existing Local Repository never initializes or overwrites them.
  • Test Connection queues the Borg check, returns a run ID immediately, and stores diagnostics and size information in the run log. Long external checks therefore no longer produce an HTTP 504 timeout.
  • Clear Cache directly removes only the manager-side cache for the selected repository, never archives or repository configuration.
  • Compact can be started directly on the repository without a backup job; active repository runs and archive mounts block the action.
  • If a previously initialized managed repository no longer has a Borg config, the list shows Repository missing. Reset is allowed only for a completely empty target directory, never deletes files, and makes Initialize available again. Jobs and repository operations remain blocked until reinitialization succeeds.
  • Archive lists are persisted in /data/archive-cache and invalidated after write operations.
  • Original, compressed and deduplicated sizes are shown in a compact vertical layout.
  • The storage guard checks the actual local filesystem for managed repositories. External SSH repositories can opt into a separate df -m probe before backup, every 15 seconds during borg create, and once after the job. The repository list shows current filesystem usage next to status/ID; reaching the threshold stops Borg gracefully.
  • Repositories can be disabled directly from the list. Configuration and jobs remain stored, but are not executed manually or by schedules until the repository is enabled again. Disabled repositories are excluded from System Diagnostics and storage probes; managed forced-command access is not published while disabled.

6. Backup jobs

The job list shows source size and file count. Values are updated exactly from completed Borg backups. A manual refresh performs a repository-independent live scan on the source device, counts each configured source separately and applies the job exclusion patterns, cache tags, `nodump` and the configured filesystem boundary. It creates no archive; patterns that cannot be mirrored safely downgrade the source-stat quality instead of producing false precision. Sub-mounts are counted only when “Stay on each source filesystem” is disabled; otherwise the scan log explicitly lists them as skipped. A job connects one device to one repository and defines sources, exclusions, archive name template, compression, Borg create options and retention. The list can be sorted by name, status, device or repository, with the choice stored per user and browser. New archives use a compact permanently reserved prefix; historic prefixes remain assigned.

The archive browser behaves like a file browser with breadcrumb navigation and columns for size, type, permissions, owner/group and modification time. More opens a compact action bar grouped into Checks, Repository Access, Storage Maintenance and Management. It contains connection test, Borg check, job info, repository access, prune, compact, enable/disable, edit and delete. Access setup affects only this job's device/repository pair. Disabled jobs keep all settings and schedule assignments but are not started; active or queued runs must finish first.

Write operations for the same repository are serialized; different repositories may run in parallel. Manager commands use /data/borg-cache/repository-<ID>, while device commands use $HOME/.cache/borgbackup-manager/repository-<ID>. When SSH uses root, $HOME is /root; a path below /root/.cache is therefore a local device cache, not the repository. Backup, prune, compact and archive changes invalidate the archive cache. Compact uses verbose Borg output and reports the estimated freed space when Borg provides it.

7. Central schedules

Schedules are managed independently of jobs. They can target selected devices, selected jobs or all jobs in a repository; later matching jobs are included automatically. A job without assignment remains manual.

Daily, weekdays, weekends, selected weekdays, monthly and custom cron expressions are supported, including multiple times. Schedules can be enabled individually. A schedule runs in phases: all backups first, then all configured prune runs, followed by at most one compact per affected repository. Manual jobs may optionally enable prune and then compact in their retention settings; the repository remains reserved until that chain finishes. Each schedule can also define its own concurrency cap: 0 uses only the global limit, while 1 queues jobs across different repositories one after another. Manual source-statistics scans count against the global limit and also have their own cap (default 1), while not reserving repository or mount capacity.

8. Runs, queue and live log

The Runs page filters by running, queued, successful, warning, failed or cancelled, with search and configurable list length. A run can be opened, cancelled, retried or deleted after completion. At most one Borg action runs per repository, while the global setting and optional schedule cap can also limit concurrency across different repositories. FIFO planning fills free slots with eligible runs so an older run that is itself blocked does not unnecessarily stop independent repositories. Queued logs identify the repository, schedule or global limit and, when available, the blocking run ID. Only live manager tasks consume slots, so orphaned run state cannot block the queue indefinitely. For remote backups, cancellation first closes the supervised control channel. The wrapper on the device then stops the complete Borg process group with SIGINT and confirms its exit before SSH and the queue slot are released; escalation to SIGTERM and SIGKILL is used only when the process does not respond. Automatic break-lock is intentionally avoided for repositories shared by multiple clients. The remote wrapper no longer requires the GNU-specific env --default-signal extension, so clients using BusyBox or older coreutils releases are supported as well.

The live dialog shows summary, trigger type, schedule, Borg version, saved backup sizes and readable output. Warning causes are collected line by line while Borg is running and are stored permanently on the run. Changed files (C), file access errors (E), disappeared paths, permission, I/O and pattern warnings therefore remain visible even when large amounts of output follow or the visible log is truncated. When the full file list is disabled, the manager requests A/M/C/E: A and M are used only for live counters, while C and E also remain available for warning diagnosis; unchanged U items are not requested. In addition, every running backup shows Borg live progress independently of the file-list option: processed files, original/compressed/deduplicated data volumes and the current path. The live view adds A/M/C/E counters and the latest matching path. The Network tile shows cumulative upload/download traffic since job start on the client interface selected by routing to the repository and keeps those totals after completion. The live-dialog header additionally shows up to three active client interfaces with IP and current rate, while BBM traffic remains a separate indicator. With a usable source baseline, each backup freezes the last known source size and file count when the run is queued. Borg O/N are subtracted directly from that baseline. Remaining time is calculated from the remaining bytes with a fixed 1-Gbit/s interface assumption and 80% usable throughput (0.8 Gbit/s effective); remaining file count adds only a fixed small-file penalty. Measured network throughput, short-term Borg rates, files-cache phase detection and previous total runtimes are not used. If the frozen byte baseline is exceeded, no remaining time is shown. A/M/C/E remain live counters only, and unchanged U items are still not requested. If Borg returns only rc 1 without a concrete detail line, the dialog explicitly shows “Cause not emitted”. Technical Details contains the command, stdout and filtered stderr.

Complete logs are stored in /data/run-logs/run-ID.log. Large file lists are written as buffered raw-byte blocks; ordinary item paths are neither fully decoded nor stored in SQLite. Only bounded paths for actual warning causes remain in the structured warning summary. With the dialog closed, only run status is polled. An open live log transfers only new bytes from its file offset; the initial request and background polling are protected against duplicate or stale responses. The active browser view remains bounded and loads the configured complete head/tail view once after completion. Retention, maximum file size, UI display limit and cleanup are managed in system settings.

9. Archive list, filters, browser and export

  1. Select a repository and click Show Archives. The view reads only the persistent cache and never starts a Borg scan inside the HTTP request.
  2. If no cache exists yet or changes were made outside the manager, Reload from Repository queues a background run. The archive view reloads from the new cache after that run completes.
  3. Archives are always sorted newest first.
  4. Device resolution first uses current or historic archive series, then the Borg hostname and archive name. Generic formats such as docker-2026-07-17_03-20 are supported.
  5. Checkpoint archives can be included separately.
  6. Each row shows duration, files, original, compressed and deduplicated size; Details adds start, end, hostname, user, comment and archive ID.
  7. The browser works without FUSE and provides file-browser breadcrumbs, size, type, POSIX permissions, owner/group and modification time. A selection can be passed to restore or exported as TAR.GZ for a matching managed repository job.
  8. Administrators can select one or multiple archives and delete them in one repository-wide action. A mixed selection is labelled “Multiple devices”; Compact optionally runs once after all deletions.
  9. Restore and rename require an unambiguous backup-job assignment.

11. Manager backup, cache backup and restore

Since v1.0.77 manager state and Borg caches are separate backup types. A newly created manager backup contains only the manager/security data needed for BBM recovery; Borg caches are stored only in a separate cache artifact.

  • Manager backup: mandatory AES-256-GCM encrypted .bbm with a non-stored passphrase of at least twelve characters. It contains databases, master key, settings, SSH/repository keys, Borg keyfiles and TLS files, but no Borg caches.
  • Cache backup: separate artifact containing the selected manager cache /data/borg-cache + /data/borg-security, client caches $HOME/.cache/borgbackup-manager/repository-<ID>, or both.
  • Cache encryption: enabled and recommended by default, but may be disabled. Encrypted cache artifacts use .bbm; deliberately unencrypted artifacts use .zip.
  • Live progress: both backup types show phase, progress bar and status log. Client-cache collection reports device/repository, Client x/y and transferred bytes. Reloading the page resumes an active status.
  • Consistency: cache backup requires no queued or active runs. Disabled devices are skipped; an unreachable enabled device aborts client-cache collection. Locks and symbolic links are excluded.
  • Restore: manager backups restore complete manager state. Cache artifacts are handled separately: explicitly restore manager cache or select saved client caches individually. Existing caches are preserved under timestamped safety names first.
  • Legacy: combined v1.0.75/v1.0.76 backups remain compatible for both manager restore and their embedded cache restores.
  • Upload backup: supported manager or cache artifacts can be imported; type, filename, limits and structure are checked and existing files are never overwritten.
  • Manage Borg cache: manager and client state is checked only on demand. Client scans can target all devices or a multi-selection of specific devices. Each selected client is checked for the BBM client cache $HOME/.cache/borgbackup-manager/, legacy Borg cache $HOME/.cache/borg/ plus alternate historical cache roots derived from BORG_CACHE_DIR, XDG and the SSH user home, and Borg security state under $HOME/.config/borg/security/ or BORG_SECURITY_DIR. Security rows expose location and manifest-timestamp; clearly older non-active duplicates for the same location are identified. A legacy Borg cache sharing the Borg repository ID of a current BBM repository is treated only as assigned, not as used by BBM, and can be deleted manually. Active BBM client caches have a separate reset action with a warning; repository data and Borg security state are preserved, but the following backup may take longer while Borg rebuilds the cache. Reset is blocked while runs or a manager/cache backup are active. Unknown regular Borg/security directories may be selected manually but are never preselected. Restore safety copies remain separate. Every deletion performs a fresh scan first. Manager-side /data/borg-cache and /data/borg-security use the same conservative checks including manifest-timestamp.
  • Server migration: restore the manager artifact first with restore-backup.sh, then restore the separate cache artifact through the Web UI if needed.

12. Notification center

Administrators can send backup, repository, schedule and other run events through SMTP, a generic JSON webhook, Discord or Telegram. Failures and warnings are selected by default; successful events can be enabled optionally. Warning messages include the concrete affected files or paths stored in the structured Borg warning summary.

System status: The “System status: outage and recovery” option connects the real BBM health watchdog to the enabled channels. Database, authentication/security store, scheduler and repository SSH are monitored independently from APScheduler. Two matching failed checks confirm an outage; two healthy checks then produce one recovery notification.

  • Secrets: SMTP password, webhook URL and Telegram token are encrypted in the security database and are never returned to the Web UI.
  • Testing: every enabled channel has its own test action.
  • Delivery log: records success or the concrete delivery error without changing the Borg run result.
  • Diagnostic excerpt: filtered and bounded, and can be disabled completely.
  • Webhook: generic JSON containing event, severity, title, message, run ID and timestamp, or a Discord-compatible embed.

Delivery starts only after repository and concurrency queue slots have been released. A slow or unavailable notification service therefore does not hold up subsequent backups.

13. Users, roles and personal preferences

Administrator

Manages infrastructure, jobs, schedules, system settings, manager backups and users, plus all operational functions.

User

Read-only viewer role for the dashboard, lists and summarized run status, plus personal language and appearance. Operational actions, full logs, archives and configuration remain administrator-only.

Every user can open Appearance & Language and save their language (German or English) and theme (automatic, light or dark) individually. These values do not change a system-wide setting. The quick theme button also changes only the current user account.

Administrators can create users, change role and enabled status, set temporary passwords and require a password change. The current account and the last active administrator are protected.

15. Diagnostics, mobile view and safe operation

  • Sign-in: source-scoped rate limits protect expensive password verification without allowing third parties to lock an account globally.
  • Sessions: cookies are Secure, HttpOnly and SameSite=Strict, with absolute and idle expiry limits.
  • Proxy trust: forwarded headers are accepted only from explicitly configured proxy networks.
  • Readiness: /api/ready and the minimal status endpoint /api/health/strict; detailed components are administrator-only at /api/system/health.
  • System diagnostics: Borg version, repository base mount, all sub-mounts plus enabled external repository filesystems with freshly probed usage, storage guard, sshd, forced commands and repository access. Access checks run directly as Web user borg; the root-only sshd -t check is handed off at container startup. Disabled devices are excluded from expected authorized_keys counts. Log tabs switch between sshd, borg-serve and a persistent debug/error log for unexpected tracebacks and background failures.
  • Repository port: allow port 2222 through the firewall only for known clients.
  • Repairs: automatic borg check --repair and break-lock are deliberately not offered.
  • Destructive actions: verify selection and backup state before prune, compact, archive deletion and restore.
  • Mobile view: Menu opens navigation; tables become cards and actions wrap cleanly. The live dialog has its own vertical scroll area and locks background page scrolling so progress, network, diagnostics and log output remain fully reachable.
